# Token accounting

How Atlas counts tokens, what the numbers on the Stats page mean, and how a monthly limit is enforced.
Written from the 2.0.3 implementation.

## How counting works

Atlas uses the number a model reports whenever there is one. Only when nothing is reported does it estimate.
Every figure is one of three kinds, and they are kept apart:

| Kind | Meaning | Lifetime total | Monthly limit |
|---|---|---|---|
| **Confirmed** | The provider or model server reported it. | yes | yes |
| **Estimated** | The request succeeded, nothing was reported, Atlas estimated. | yes | yes |
| **Uncertain** | The request may have reached the provider and then failed or was cut off, so it may have been billed. | **no** | **yes** |

Uncertain tokens are an input estimate only (the output of a failed request is unknowable). If a failed response
still contained a usage block, the provider counted it, so it is confirmed instead.

A request that never left this computer (no key, bad address, no connection, refused, TLS failure, or a limit
reached before sending) costs nothing and is not counted at all. A request the provider turned away with a client
error (a bad key, a rate limit, a spending limit) counts as a request but adds no tokens.

### What "may have reached the provider" means

| What happened | Counted as |
|---|---|
| Refused by Atlas before sending (limit, pause, burst guard) | nothing |
| Could not connect (DNS, refused, TLS handshake, connect timeout) | nothing |
| Provider answered 4xx (except 408) | the request, no tokens |
| Timeout after sending, reset mid-reply, a 5xx or 408, an unreadable or unexpected reply | uncertain |
| You pressed Stop while the request was in flight | uncertain |

An error that cannot be classified is treated as uncertain, which is the safe side for a limit.

## What each provider reports

The providers disagree about what "input" includes. Atlas normalises them so cached tokens are never added twice:

| Provider | Input counted | Cached input |
|---|---|---|
| OpenAI-compatible | `prompt_tokens` (cached tokens are already inside it) | `prompt_tokens_details.cached_tokens` (or the equivalent field some compatible servers use) |
| Anthropic | `input_tokens` **plus** cache reads **plus** cache writes (Anthropic reports the three separately) | cache reads |
| Gemini | `promptTokenCount` plus tool-use prompt tokens | `cachedContentTokenCount` |

Output counts reasoning tokens where the provider bills them as output. Gemini reports thinking tokens beside
the answer tokens rather than inside them, so Atlas adds them, and checks the provider's total so it never counts
them twice.

Cached input is a *part of* input. It is shown as "of which cached" and never added to a total.

## How the estimate works

The estimator looks at the text, not just its length:

1. **By script.** Each character is weighted by what kind it is: English letters and punctuation are cheap, digits
   cost more (many tokenizers split numbers digit by digit), accented and Cyrillic letters sit in between, Chinese,
   Japanese and Korean cost more per character, emoji cost the most, and joiners and combining marks are counted
   as part of the character they belong to rather than as new ones.
2. **By kind of text.** Each paragraph is classified as prose, code, JSON or logs, and code, JSON and logs get a
   multiplier because they produce more tokens per character than prose. A prompt that is half prose and half pasted
   code is estimated paragraph by paragraph.
3. **By model, once learned.** Whenever a model reports a real count for a request Atlas also estimated, the ratio
   between them is folded into a moving average for that model and kind of text. After 20 samples the estimate is
   scaled by it. Only ratios and counts are stored, never text, and the table can be reset.
4. **The whole request.** Tool definitions and response schemas that are sent with a prompt are billed as input too,
   so they are counted (as JSON).

The weights live in `packages/core/src/token-weights.json`, read by both the Rust and the TypeScript estimator. A
test requires the two to agree to the token on every shared fixture.

An estimate is always labelled as one. It is never shown as a measurement.

### How close is it?

See [TOKEN-ACCURACY.md](TOKEN-ACCURACY.md), regenerated by `node scripts/token-calibrate.mjs` against a real local
model's own token counts. Estimates for ordinary English are within a few percent; other scripts and structured text
are looser. The honest summary: it is a good estimate, not a tokenizer, and a provider's own figure always wins.

## Monthly limits

A limit you set for a provider counts **confirmed + estimated + uncertain** tokens in the current calendar month.
Uncertain counts because a limit protects money, and a request that may have been billed may have cost some. It
means a limit can trigger slightly earlier than your provider's bill would suggest, never later.

The lifetime total on the Stats page is confirmed + estimated only.

## Days before the split was recorded

Before 2.0.3, confirmed and estimated tokens were one number. Atlas does not guess how that old number divides: the
Stats page shows those days as "from before this split was recorded".

## Cost estimates

Dollar figures are an estimate from prices you enter, not a bill. Your provider's dashboard is the only real figure.
Uncertain tokens are shown separately ("may have been billed") and are not in the dollar estimate.
